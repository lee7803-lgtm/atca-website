## 1. 版本定位

ITCA 官网 V1.3 不是对 V1.2 的推翻重做，而是在 V1.2 已完成的认证申请、会员申请、后台审核、申请进度查询、证书核验等基础业务闭环上，进行架构升级、公开核验收口、会员核验补齐、后台治理增强和后续运营模块预留。

V1.3 的核心定位为：

1. 完成 .NET API 线上部署与 Preview 接入验证；
2. 完成证书公开核验的安全访问机制；
3. 保留证书详情页，但必须通过双字段验证后的短期核验凭证访问；
4. 补齐会员查询 / 会员公开核验；
5. 将正式管理员账号体系、操作日志、编号规则、PDF 证书、自动通知、在线支付、用户系统纳入 V1.3 分阶段规划；
6. 为数据中台实时对接、多语言国际站完整体系做架构预留；
7. 认证申请、Storage、补充资料、证书生成、发证下发不在 V1.3 初期强行一次性迁移，应按迁移边界逐步推进。

## 3. 目标技术架构

V1.3 的目标架构为：

```text
Next.js 官网 / 后台界面
+ .NET API 后台业务接口
+ Supabase PostgreSQL 正式数据库
+ Supabase Storage 文件存储
```

各层职责如下：

| 层级 | 职责 |
|---|---|
| Next.js | 官网页面、后台界面、表单交互、页面路由、前端展示、API 调用层 |
| .NET API | 正式后台业务逻辑、公开查询接口、后台审核接口、权限接口、编号生成、支付接口、通知接口等 |
| Supabase PostgreSQL | 正式业务数据库 |
| Supabase Storage | 正式文件存储，尤其是认证材料、证书照片、补充资料等 |

V1.3 不应继续在 Next.js API Routes 中无边界扩展核心后台业务逻辑。短期内可以保留已有 Next.js API 作为 fallback 或过渡层，但新增核心业务应逐步向 .NET API 收拢。

8. 验证 Preview 是否真实调用线上 .NET API；

### 5.3 验收标准

| 验收项 | 标准 |

| Supabase PostgreSQL | 线上 .NET API 可连接数据库 |

## 6. 证书核验机制

### 6.1 基本原则

V1.3 必须保留证书详情页，但证书详情页不是公开裸链，不能凭证书编号直接访问。

公众必须先通过 `/certificate-query` 输入：

```text
证书编号 + 持证人姓名
```

验证通过后，系统生成短期核验凭证。只有带有效核验凭证的证书详情页，才允许展示证书公开详情。

### 6.2 保留页面

保留证书详情页：

```text
/certificates/[certificateNo]
```

但该页面不能仅凭 `certificateNo` 读取和展示证书详情。

### 6.3 公众核验唯一入口

公众证书核验唯一入口：

```text
/certificate-query
```

用户输入：

```text
证书编号
持证人姓名
```

### 6.4 正确访问流程

#### 第一步：进入证书核验页

```text
/certificate-query
```

#### 第二步：提交双字段验证

建议接口：

```text
POST /api/certificates/verify
```

请求示例：

```json
{
  "certificateNo": "ITCA-TAO-2026-000001",
  "holderName": "张三"
}
```

后端验证：

1. 证书编号是否存在；
2. 持证人姓名是否匹配；
3. 证书是否允许公开核验；
4. 证书状态是否可展示；
5. 是否只返回公开字段；
6. 不返回申请材料、联系方式、后台备注、Storage path 等敏感信息。

#### 第三步：生成短期核验凭证

验证成功后，后端返回：

```json
{
  "success": true,
  "certificateNo": "ITCA-TAO-2026-000001",
  "detailUrl": "/certificates/ITCA-TAO-2026-000001?vt=短期核验凭证"
}
```

其中：

```text
vt = verification token
```

也可以理解为：

```text
verification session id
```

#### 第四步：访问证书详情页

前端跳转：

```text
/certificates/ITCA-TAO-2026-000001?vt=xxxxx
```

详情页加载时，必须再次请求 .NET API：

```text
GET /api/certificates/ITCA-TAO-2026-000001/detail?vt=xxxxx
```

后端必须检查：

1. `certificateNo` 是否与核验凭证绑定；
2. `vt` 是否有效；
3. `vt` 是否过期；
4. `vt` 是否用于证书详情访问；
5. 证书是否仍允许公开核验；
6. 证书状态是否仍可展示。

通过后才返回证书公开详情。

### 6.5 直接访问详情页的处理规则

如果用户直接访问：

```text
/certificates/ITCA-TAO-2026-000001
```

但没有有效 `vt`，页面不得展示证书详情。

页面应显示：

```text
请先完成证书核验。
为保护持证人信息，请返回证书查询页面，输入证书编号与持证人姓名进行核验。
```

按钮文案：

```text
前往证书核验
```

跳转：

```text
/certificate-query
```

### 6.6 核验凭证设计

建议新增服务端短期核验凭证机制。

建议表名：

```text
certificate_verification_sessions
```

字段建议：

| 字段 | 说明 |
|---|---|
| id | 核验会话 ID |
| certificate_no | 证书编号 |
| holder_name_hash | 持证人姓名哈希，不建议直接存明文 |
| purpose | 用途，例如 certificate_detail |
| created_at | 创建时间 |
| expires_at | 过期时间 |
| used_count | 使用次数 |
| ip_address | 可选，用于风控 |
| user_agent | 可选，用于风控 |

有效期建议：

```text
15 分钟
```

V1.3 初期建议规则：

```text
15 分钟内有效；
只能用于绑定的 certificateNo；
过期后必须重新回到 /certificate-query 验证。
```

### 6.7 证书详情页可展示字段

| 字段 | 是否展示 |

## 11. 编号规则

### 11.1 申请编号

正式采用：

```text
ARID = Application Reference ID
```

建议格式：

```text
道士认证申请编号：ARID-ITCA-TAO-2026-000001
个人会员申请编号：ARID-ITCA-M-2026-000001
机构会员申请编号：ARID-ITCA-ORG-2026-000001
```

### 11.2 正式业务编号

```text
道士资格认证证书编号：ITCA-TAO-2026-000001
个人会员编号：ITCA-M-2026-000001
机构会员编号：ITCA-ORG-2026-000001
```

### 11.3 支付与通知编号

```text
支付订单编号：PAY-ITCA-2026-000001
通知记录编号：NTC-ITCA-2026-000001
```

### 11.4 编号规则要求

1. 申请编号、证书编号、会员编号不得混用；
2. TAO、M、ORG 前缀必须与业务类型一致；
3. 需要支持旧编号兼容；
4. 需要支持编号唯一性检查；
5. 需要支持后台查看编号来源；

## 22. 最终确认结论

V1.3 正式采用以下证书核验方案：

```text
V1.3 必须保留证书详情页。
但证书详情页不是公开裸链，不能凭证书编号直接访问。
公众必须先通过 /certificate-query 输入证书编号 + 持证人姓名。
验证通过后，系统生成短期核验凭证 vt。
只有带有效 vt 的 /certificates/[certificateNo] 页面，才允许展示证书公开详情。
vt 过期、缺失、错误或与证书编号不匹配时，详情页不得展示证书内容，必须提示用户返回证书核验页重新验证。
```

V1.3 当前最优先事项为：

```text
先完成 .NET API 线上部署与 Preview 接入验证，
再完成证书核验机制收口，
然后补齐会员公开核验。
```

在此之前，不建议启动支付、PDF、用户系统等大规模功能开发。
