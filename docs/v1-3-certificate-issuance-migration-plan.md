# V1.3 Certificate Issuance Migration Boundary

This document records the current certificate issuance, delivery, certificate record, and status linkage behavior. It is a migration boundary note only. The live certificate issuance flow should remain in Next.js until .NET can own the full transactional write path safely.

## Current chain

Admin certificate issuance starts from the certification application detail page:

```text
app/admin/certification-applications/[id]/page.tsx
app/admin/certification-applications/ReviewForm.tsx
```

The detail page loads:

- The certification application through `getCertificationApplicationById`.
- The certificate record through `findCertificateByApplicationId`.
- Admin-only signed URLs for application attachments and certificate photo preview.
- Material review controls for each required review item.

The review form sends all admin review fields plus an action to:

```text
PATCH /api/admin/certification-applications/{id}
```

There are no separate live route files at:

```text
app/api/admin/certification-applications/[id]/certificate/route.ts
app/api/admin/certification-applications/[id]/deliver/route.ts
```

The current route multiplexes status updates, material review updates, certificate generation, delivery marking, delivery correction, and archive actions.

## Admin entry

Certificate generation button:

```text
app/admin/certification-applications/ReviewForm.tsx
```

It is shown only when:

- Initial application status is `approved`.
- No certificate number is already loaded for the application.

The button calls:

```json
{
  "action": "generate_certificate",
  "generateCertificate": true
}
```

The shared request body also includes review note, internal review note, applicant feedback, approved path, approved level, committee review note, and taoist rank values from the form.

Delivery button:

```text
app/admin/certification-applications/ReviewForm.tsx
```

It is shown only when:

- A certificate record exists.
- `deliveryStatus` is not `delivered`.
- Initial application status is `certificate_issued` or `cert_issued`.

It calls the same PATCH route with:

```json
{
  "action": "mark_delivered"
}
```

## Current API

Live API:

```text
PATCH /api/admin/certification-applications/{id}
```

Relevant actions:

- `update_material_review`
- `generate_certificate`
- `mark_delivered`
- `correct_not_delivered`
- `archive`
- Regular status update through `status`

The route requires a valid admin session cookie before processing.

## Issuance preconditions

The route enforces these server-side checks before creating a certificate:

- No existing certificate found by `application_id`.
- Application status is exactly `approved`.
- Final approved path exists.
- Final approved level exists.
- Final material review exists and every entry is `passed`.

The form also blocks the button with the same main checks:

- Initial status is `approved`.
- No certificate exists.
- Approved path exists.
- Approved level exists.
- All material review values are `passed`.

## Material review dependency

Material review is a JSON field on `certification_applications`.

The normalized material review keys are:

- `identity`
- `lineage`
- `credential`
- `practice`
- `recommendation`
- `ethics`
- `photo`
- `completeness`
- `international`

Certificate generation requires every normalized material review item to be `passed`. `pending`, `need_more_info`, `questionable`, and `not_applicable` all block certificate generation under the current implementation.

## certificate_photo_path dependency

The certificate record copies:

```text
application.certificatePhotoPath
```

into:

```text
certificates.certificate_photo_path
```

The admin application mapper falls back to the `photo` supporting document when `certification_applications.certificate_photo_path` is missing, but certificate generation uses the mapped `application.certificatePhotoPath`. Certification application submission and supplement submission can both affect this path.

Applicant progress query can later create a short-lived signed URL from the certificate photo path for applicant-only display after application number and contact verification. Public certificate query does not expose the raw Storage path or signed photo URL.

## Certificate number rule

The current certificate number is generated by:

```text
generateCertificateNo(date)
```

The format is:

```text
ITCA-TAO-{yyyy}-{six digit random sequence}
```

The six digit sequence is generated with `Math.random()` and padded to six digits.

The `certificates.certificate_no` column is unique, so the database can reject duplicate certificate numbers. The current route does not retry with a new number after a unique collision. It also checks for an existing certificate by `application_id` before insert, but this is not an atomic lock.

The inserted fields are:

- `certificate_no`
- `application_id`
- `holder_name`
- `taoist_name`
- `taoist_rank`
- `sect`
- `certification_path`
- `certification_level`
- `lineage_or_temple`
- `certificate_photo_path`
- `issued_date`
- `valid_from`
- `valid_until`
- `status`
- `public_query_enabled`
- `created_at`
- `updated_at`

Current values:

- `holder_name`: application applicant name.
- `taoist_name`: application taoist name.
- `taoist_rank`: approved level label.
- `sect`: application sect or lineage.
- `certification_path`: final approved path.
- `certification_level`: final approved level.
- `lineage_or_temple`: sect, lineage, and temple or organization joined together.
- `certificate_photo_path`: application certificate photo path.
- `issued_date`: current date.
- `valid_from`: current date.
- `valid_until`: current date plus three years.
- `status`: `valid`.
- `public_query_enabled`: `true`.

## certification_applications linkage

After `insertCertificate` succeeds, the route updates the application through `updateCertificationReview`:

- `status`: `certificate_issued`
- `review_note`
- `internal_review_note`
- `applicant_feedback`
- `approved_path`
- `approved_level`
- `material_review`
- `committee_review_note`
- `reviewer`
- `reviewed_at`
- `delivery_status`: `not_delivered`
- `delivered_at`: `null`
- `updated_at`

There is no `certificate_issued` boolean or `certificate_issued_at` column in the current schema. Issuance is represented by `certification_applications.status` plus the presence of a row in `certificates`.

The insert and application update are separate Supabase REST requests. If the application update fails after the certificate insert, the route attempts `deleteCertificateByNo` as best-effort cleanup.

## delivery_status and delivered_at

`mark_delivered` first confirms a certificate exists for the application.

It then updates `certification_applications`:

- `status`: `delivered`
- `review_note`
- `internal_review_note`
- `applicant_feedback`
- `approved_path`
- `approved_level`
- `material_review`
- `committee_review_note`
- `reviewer`
- `delivery_status`: `delivered`
- `delivered_at`: current timestamp

`correct_not_delivered` confirms a certificate exists, then updates:

- `status`: `certificate_issued` when current status is `delivered`; otherwise current status
- `delivery_status`: `not_delivered`
- `delivered_at`: `null`

The `certificates` row is not updated by delivery marking.

## Notification copy dependencies

The review form contains applicant feedback templates. Certificate-related templates depend on:

- `applicationNo`
- `certificateNo`

The "certificate generated" template tells the applicant that the certificate record has been generated and includes the certificate number. The "certificate delivered" template says the certificate has been delivered and points the applicant to the public verification entry.

Because these templates are composed in the admin form and can be saved with the same PATCH request, moving issuance or delivery writes without preserving response shape and refresh behavior can break the admin notification workflow.

## Public verification dependencies

The public certificate query page calls:

```text
GET /api/certificates/query?certificateNo={certificateNo}&holderName={holderName}
```

The Next.js client first tries the .NET API base URL and falls back to the Next.js route when appropriate.

The query requires:

- Exact certificate number.
- Exact holder name.
- `public_query_enabled = true`.

The public response maps these `certificates` fields:

- `certificate_no`
- `holder_name`
- `taoist_rank`
- `certification_path`
- `certification_level`
- `issued_date`
- `valid_from`
- `valid_until`
- `status`

It also returns a computed issuer and computed `detailUrl`.

Public display masks the holder name and does not display:

- Application number.
- Contact information.
- Certificate photo.
- Raw Storage path.
- Uploaded materials.
- Applicant feedback.
- Internal review note.

## Application progress dependencies

The application progress query identifies certification applications by application number and contact:

```text
GET /api/applications/query?mode=number&applicationNo={applicationNo}&contact={contact}
```

For certification applications it reads `certification_applications`, then tries to find a certificate by `application_id`.

Applicant-facing certificate fields include:

- `certificateNo`
- `certificateDetailUrl`
- `certificateStatus`
- `certificateHolderName`
- `certificateTaoistName`
- `certificationPath`
- `certificationLevel`
- `certificateLineageOrTemple`
- `certificateIssuer`
- `certificateIssuedDate`
- `certificateValidFrom`
- `certificateValidUntil`
- `certificatePhotoUrl`
- `certificatePhotoRecorded`
- `deliveryStatus`
- `deliveredAt`

The page displays whether a certificate has been generated, delivery status, delivery time, certificate number, public verification entry, and a printable applicant-only certificate information block. The photo URL is short-lived and only returned after application number plus contact verification.

## Certificate detail access status

The current route:

```text
app/certificates/[certificateNo]/page.tsx
```

does not render certificate details directly. It instructs users to verify through the certificate query page with certificate number and holder name.

The page states that any future independent certificate detail page should use a random token, short-lived token, or authorized verification link. This is an intentional access-control boundary and should not be weakened during issuance migration.

## Information isolation rules

Current intended isolation:

- Public certificate query requires certificate number and holder name.
- Public query only reads records with `public_query_enabled = true`.
- Public query does not expose raw Storage paths.
- Public query does not expose certificate photo URLs.
- Public query does not expose application number or contact data.
- Public query does not expose upload materials, applicant feedback, committee notes, or internal review notes.
- Applicant progress query requires application number plus contact.
- Applicant progress query can show certificate photo through a short-lived signed URL only after applicant verification.
- Admin signed URL previews require an admin session.
- Service role access remains server-side.

## Current risks

Duplicate certificate generation:

The route checks for an existing certificate before insert, but the check and insert are separate requests. Concurrent clicks or retries can race. The unique `certificate_no` constraint only protects duplicate numbers, not duplicate rows for the same `application_id`.

Status race:

Admin status changes, material review updates, certificate generation, delivery correction, and delivery marking all use the same PATCH route without compare-and-swap conditions.

Certificate row generated but application status not updated:

The certificate insert can succeed and the following application update can fail. Cleanup is best-effort and not guaranteed.

Application status updated but certificate row not generated:

The current issuance order reduces this specific risk by inserting the certificate first. Future migrations must avoid reversing this without a transaction.

Missing `certificate_photo_path`:

The route does not explicitly reject issuance when `certificate_photo_path` is missing. It can insert a certificate with a null certificate photo path.

Material review not passed but certificate issued:

The server blocks generation unless all normalized material review values are `passed`. Any migration that changes normalization or treats `not_applicable` as pass would change issuance behavior.

`public_query_enabled` misconfiguration:

Generation always sets `publicQueryEnabled` to `true`. Public query visibility depends on this flag.

Incomplete revocation and expiry flow:

The schema supports certificate statuses `pending`, `valid`, `revoked`, and `expired`, and application statuses include `revoked`, but the current admin flow does not provide a complete certificate status transition, revocation, or expiry management workflow.

Public verification field overexposure:

The current public DTO is narrow. Future .NET endpoints must not expose `certificate_photo_path`, contact fields, application fields, uploaded material metadata, or review notes.

## Migration decision

Do not migrate live certificate generation or delivery marking in this round.

Reasons:

- Certificate generation writes both `certificates` and `certification_applications`.
- Generation depends on all `material_review` entries being `passed`.
- Generation copies `certificate_photo_path`.
- Admin buttons, notification templates, and refresh behavior depend on the current response shape.
- Applicant progress query depends on generated certificate fields and delivery fields.
- There is no database transaction or application-level lock around issuance.
- .NET currently owns public certificate query/detail reads and application progress reads, but not the full certification admin write workflow.
- Moving issuance now can break the V1.2 certificate generation, public verification, and applicant progress closure.

This round keeps the live Next.js issuance route unchanged and reserves the migration boundary in documentation.

## Future .NET API split

Recommended future endpoints:

```text
POST /api/admin/certification-applications/{id}/certificates
```

Owns issuance precondition checks, certificate number generation, certificate insert, application status linkage, delivery defaults, and transactional rollback.

```text
PATCH /api/admin/certificates/{certificateNo}/delivery
```

Owns delivery marking and delivery correction after it can safely resolve certificate and application linkage.

```text
PATCH /api/admin/certificates/{certificateNo}/status
```

Owns certificate status transitions such as valid, revoked, and expired, with audit trail and application status linkage rules.

```text
GET /api/admin/certificates/{certificateNo}
```

Returns admin-authorized certificate detail, linked application summary, delivery state, and audit information without relying on public query DTOs.

```text
GET /api/certificates/query
```

Keeps public read-only verification narrow and information-isolated.

## Recommended migration route

Step 1: Keep existing certificate generation unchanged.

Step 2: Let .NET own read-only public query and detail behavior. This has already been introduced for public certificate reads and guarded detail access.

Step 3: Let .NET own a read-only admin issuance precheck endpoint. It should validate status, existing certificate, approved path, approved level, material review, photo path presence, public query settings, and possible race warnings without writing.

Step 4: Let .NET own certificate generation writes using a database transaction. It should lock or conditionally update the application, insert one certificate per application, update application status, and handle certificate number collision retry.

Step 5: Let .NET own delivery marking and correction after issuance writes are stable.

Step 6: Let .NET own certificate status changes, revocation, expiry, and related application status linkage.

Step 7: Unify certificate number generation with a database-backed yearly sequence or another collision-resistant rule.

## Rollback strategy

During any future migration:

- Keep the current Next.js PATCH issuance route available as a fallback until .NET write behavior is proven with real staging data.
- Gate .NET issuance behind an explicit server-side feature flag.
- Do not change the public certificate query DTO during issuance migration.
- Preserve the current admin response shape so the review form can continue to display generated certificate numbers.
- If .NET issuance fails, return to the existing Next.js route without changing certificate number format or table structure.
- Add reconciliation checks for certificate rows whose linked application status is not `certificate_issued` or `delivered`.
- Add reconciliation checks for applications in issued states without a linked certificate row.

## Next round recommendation

Recommended next low-risk round:

1. Add a read-only admin certificate issuance precheck document or endpoint contract for .NET.
2. Define the transactional write requirements for .NET issuance.
3. Define one-certificate-per-application protection before live migration.
4. Define revocation and expiry state transition rules.
5. Keep live certificate generation and delivery marking in Next.js until those safeguards are implemented and tested.
