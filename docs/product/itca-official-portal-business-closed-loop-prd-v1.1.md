## 2. 项目背景

ITCA 官网已经不再是单一展示型官网。V1.3 已经形成申请、审核、证书、核验、支付规划、通知日志、后台基础资料管理和审计基础；V2.0 导航升级进一步补齐协会门户、发展中心、会员认证、证书查验、发展合作和数据中心的前台结构。

本 PRD v1.1 的任务，是把现有官网、V1.3 兼容规则、V2.0 导航升级、会员认证、证书核验、数据中心、后台运营、财务付款、风控合规、争议处理、图标视觉语义等内容合并成一份整体总蓝图。补充矩阵文件仍保留，但只作为细节附录；主 PRD 本身必须独立可读。

## 3. 当前系统基础与 V1.3 兼容规则

### 3.1 已有基础

- V1.3 已有申请、后台审核、证书记录、公开核验、通知日志、审计日志、会员公开核验、证书 vt 详情访问和私有 Storage 上传基础。
- 证书详情页采用“证书编号 + 持证人姓名核验成功后获得短期 vt 凭证”的访问规则，当前 vt 有效期为 15 分钟。
- 会员公开核验采用会员编号与姓名/机构名称组合查询，只返回公开 DTO 字段。
- 认证附件服务端上传至私有 Storage bucket，支持 PDF/JPG/JPEG/PNG，单文件不超过 2MB。
- 后台已有管理员账号和 audit_logs 基础，同时 legacy `ADMIN_PASSWORD` 仍需兼容。

### 3.2 编号兼容

继续兼容现有编号体系，不得因为 v1.1 蓝图升级覆盖历史编号。

```text
申请编号：ARID-ITCA-M / ORG / TAO-YYYY-随机或序号尾号
个人会员编号：ITCA-M-YYYY-随机或序号尾号
机构会员编号：ITCA-ORG-YYYY-随机或序号尾号
道士认证证书编号：ITCA-TAO-YYYY-随机或序号尾号
支付订单编号：PAY-ITCA-YYYY-随机或序号尾号
通知记录编号：NTC-ITCA-YYYY-随机或序号尾号
```

规则：

- ARID 只代表申请引用编号，不代表正式会员、正式证书或付款完成。
- 正式会员编号只在会员审核通过并登记后生成。
- 正式证书编号只在证书生成后存在，公众证书核验使用正式证书编号，不使用申请编号。
- 新编号规则只能作为未来新产品或新证书类型配置，不影响历史查询和已签发证书。
- 历史 `application_no` 继续可用于申请进度查询和兼容查询。
- 公众会员查询优先查正式 `member_no`，查不到时可兼容旧 `application_no / legacy_member_no`。

### 3.4 迁移原则

- 历史数据只增补字段，不直接重写。
- 历史编号保持永久可查。
- 新状态机必须映射旧状态。
- 历史证书文件继续可验证。
- 付款订单和凭证不得丢失。
- 管理后台应提供历史数据标记。
- 不得因为 v1.1 蓝图升级破坏 V1.3 已完成闭环。

### 3.9 V1.3 已开发安全与隐私边界

- 证书公开核验必须通过 `/certificate-query` 输入证书编号和持证人姓名；详情访问依赖短期 `vt`，当前有效期为 15 分钟。
- `vt` 绑定证书编号，不包含联系方式、材料、Storage path、后台备注或管理员信息。
- `/certificates/[certificateNo]` 不能仅凭路径中的证书编号展示详情。
- `/application/query` 必须校验申请编号和登记联系方式，不能只凭申请编号返回申请详情。
- 认证附件和证书照片来源文件位于私有 Storage，不得在公开接口返回原始 path。
- 后台附件预览和申请人证书照片展示只能使用短期签名 URL 或服务端代理。
- 通知 payload、支付 metadata、provider response 和后台日志必须脱敏 token、secret、key、password、connection、storage_path、vt 等敏感字段。
- `admin_users.password_hash` 不得出现在前端、日志、文档示例或导出文件中。
- `ITCA_ADMIN_API_TOKEN` 只用于服务间鉴权，不代表真实管理员身份；真实操作人必须通过 actor header 或审计字段记录。
- 公开会员核验只返回会员编号、公开名称、会员类型、状态、登记机构、登记日期、通过日期和说明。

### 3.10 V1.3 与 v1.1 的功能承接关系

| v1.1 模块 | 必须承接的 V1.3 逻辑 | 新增扩展方向 |
| --- | --- | --- |
| 用户中心 | 申请进度、补件、证书摘要、支付订单、通知日志、会员有效期、历史申请认领。 | 统一登录后的个人工作台，但保留未登录公开查询。 |
| 会员中心 | `applications` 的会员申请、`member_no`、有效期、续期状态、公开核验兼容 `application_no`。 | 会员权益、续期订单、公开资料授权、机构主页。 |
| 认证中心 | `certification_applications` 的申请、材料、补件、审核、证书生成、下发、PDF 和 vt 核验。 | 复审、专家审核、争议、暂停/恢复/撤销。 |
| 财务中心 | `payment_orders`、`payment_events`、凭证上传、manual/none provider、后台确认和取消。 | 产品价格、收据、退款、网关、对账。 |
| 通知中心 | `notification_logs`、provider=none、模板、发送状态、失败记录和脱敏策略。 | 真实邮件、手动重发、队列、WhatsApp/短信预留。 |
| RBAC 后台 | `admin_users`、legacy `ADMIN_PASSWORD`、`audit_logs`、`ITCA_ADMIN_API_TOKEN` 服务间鉴权。 | 细粒度角色、职责冲突、权限矩阵、二次确认。 |
| 数据中心 | 会员、认证、证书、记录处置和公开授权字段。 | 八类数据库、逐项授权、纠错、撤回公开。 |

### 3.11 V1.3 已知缺口进入 v1.1 需求池

以下不是要推翻 V1.3，而是把 V1.3 已暴露的缺口纳入 v1.1 总蓝图：

- 证书生成跨 `certification_applications` 和 `certificates`，当前不是数据库事务；后续应由 .NET API 用事务、锁或条件更新保证一申请一证书。
- 申请编号和证书编号仍需更强的数据库侧序列或原子生成策略，避免并发碰撞。
- `supplemental_submissions`、`material_review`、附件元数据当前多为 JSONB，后续如需文件级审计、清理、检索和权限，应抽象为独立表。
- 认证申请写操作仍有较多 Next.js API 逻辑；后续核心写操作要分阶段迁移到 .NET API。
- 真实邮件、WhatsApp、短信、支付网关、退款、发票和自动对账仍属于后续接入，不得在 PRD 中默认已完成。
- 管理员账号已有基础，但完整 RBAC、2FA、密码重置、账号锁定、权限 UI 和职责冲突控制仍需在 v1.1/v2.x 中补齐。
- 公众查询、申请人查询、后台查询的字段边界要继续细化并形成测试用例。
- 审计覆盖已开始，但认证材料访问、导出、证书生成、PDF、支付凭证、公开数据撤回等高风险操作仍需补审计。

## 4. 产品定位

- 风控合规体系：承接认证边界、隐私授权、道医养生边界、易学 AI 边界、未成年人、争议投诉和审计。

## 6. 产品边界

### 6.1 认证边界

- 协会认证属于协会认证建档，用于文化交流、会员服务和协会内部记录场景中的参考信息。
- 协会认证不构成政府许可、行政执业资格或法定从业资质。
- 公开证书核验只证明协会公开登记状态，不替代政府、监管机构或专业机构核查。
- “道士资格认证”等公开名称需秘书处和法务确认，PRD 中统一以“道教文化认证 / 道士认证建档”表达。

### 6.2 健康与易学边界

- 道医、中医、养生、辟谷、功法修炼内容仅作文化研究、养生知识交流和课程研修，不提供医疗诊断或治疗承诺，不替代医生建议。
- 易学、东方认知、AI 解读仅作文化参考、认知辅助和自我成长参考，不构成医疗、法律、金融、心理诊断、婚姻或人生决策建议。

### 6.3 数据与隐私边界

- 个人数据公开必须获得授权。
- 个人库默认不公开。
- 未成年人信息默认不得公开。
- 传承、师承、法脉、谱系资料需分级处理。
- 敏感材料和完整身份信息仅限授权后台查看。

## 8. 总业务闭环

1. 公开访客通过官网、内容、公告、证书查验、合作入口进入 ITCA。
2. 访客注册成为用户，补充基础资料并同意隐私政策。
3. 用户根据身份选择个人会员、机构会员、认证、导师、课程、活动、合作或数据中心建档路径。
4. 系统生成申请单和申请编号，用户提交表单和材料。
5. 涉及费用时，系统生成付款订单，用户通过 Bank Transfer 或未来支付渠道付款并上传凭证。
6. 财务审核付款，确认后推动业务进入正式审核；付款不等同业务通过。
7. 审核员初审材料，必要时请求补件；复审员或专家完成复审。
8. 审核通过后生成会员档案、机构档案、认证档案、证书档案或数据中心条目。
9. 证书签发后进入公开核验体系，证书详情继续兼容 vt 短期核验机制。
10. 会员继续参与课程、活动、发展中心、合作项目和数据中心建档。
11. 公开数据必须经过授权、审核和二次确认。
12. 运营通过通知、公告、邮件/站内信、后台待办、数据分析推动续费、复审、复访和二次合作。
13. 争议、投诉、申诉、纠错进入专项处理闭环。
14. 所有关键动作进入审计日志。

## 11. 个人会员申请闭环

### 11.1 流程

### 11.2 会员状态

| 状态 | 说明 | 前台显示 | 关键规则 |
| --- | --- | --- | --- |

| 已过期 | 有效期结束 | 已过期 | 可登录查历史，限制新权益 |

## 12. 机构会员申请闭环

### 12.1 流程

机构提交主体资料、负责人资料、联系人授权、公开字段授权 -> 生成机构申请 ARID -> 生成付款订单或人工确认 -> 机构资料审核 -> 负责人授权确认 -> 机构会员编号生成 -> 机构主页/机构库入库 -> 续期/暂停/撤销/纠错。

### 12.2 机构公开规则

- 机构公开需负责人或授权联系人确认。

- 机构资料投诉或纠错必须进入争议处理闭环。
- 机构会员编号与机构库条目应可关联，但公开字段需分开授权。

| 待面谈/线下核验 | 需进一步核验 | 待复审/待签发/已驳回 | 是 |
| 待缴费 | 需付款确认 | 待初审/待签发/已关闭 | 是 |
| 待签发 | 审核通过待证书 | 已通过/已关闭 | 是 |
| 已通过 | 认证通过 | 证书签发/复审中 | 是 |
| 已驳回 | 申请未通过 | 重新申请/已关闭 | 是 |
| 复审中 | 到期、争议或变更触发复审 | 已通过/暂停/撤销 | 是 |

### 13.3 材料规则

- 上传格式继续沿用 PDF/JPG/JPEG/PNG，单文件不超过 2MB。
- 敏感材料不得公开。
- 补件必须记录轮次、材料字段、上传时间、审核意见。
- 驳回必须写明原因。

## 14. 证书签发与核验闭环

### 14.1 证书生命周期

待签发 -> 有效 -> 到期前提醒 -> 待复核/续期中 -> 有效/已过期/暂停/撤销/作废。

### 14.2 内部状态与公众显示

| 内部状态 | 公众显示 | 说明 |
| --- | --- | --- |
| 有效 | 有效 | 显示必要公开字段 |
| 到期前提醒 | 有效 | 只通知本人，不对公众显示提醒 |
| 待复核 | 待复核 | 显示人工复核说明 |
| 暂停 | 暂停 | 显示标准说明，不展示争议细节 |
| 已过期 | 已过期 | 显示有效期已届满 |
| 已撤销 | 已撤销 | 显示撤销状态和复核入口 |
| 已作废 | 无效 | 误签发、重复签发或模板作废 |

### 14.3 公开核验规则

- 查询方式：证书编号 + 持证人姓名。
- 查询成功后生成短期 vt 详情访问凭证。
- vt 绑定证书编号，有效期当前为 15 分钟。
- 详情页不得仅凭证书编号裸链访问。
- 公众核验只展示证书编号、持证人公开名称、认证类型、签发机构、签发日期、有效期、证书状态、核验时间和标准说明。
- 不展示联系方式、证件、申请材料、Storage path、后台备注、管理员信息。

### 14.4 证书高风险操作

签发、暂停、恢复、撤销、作废均需：

- 高权限角色。
- 操作原因。
- 二次确认。
- 通知相关用户。
- 写入 audit_logs。
- 必要时进入争议处理闭环。

## 15. 财务订单与付款闭环

### 15.1 当前定位

现阶段兼容 Bank Transfer，不破坏现有付款订单和付款凭证审核流程。未来 PayPal / Stripe / FPX / ToyyibPay 只作为预留，不在本轮实现。

### 15.2 流程

生成订单 -> 用户付款 -> 上传凭证 -> 财务审核 -> 通过/驳回 -> 用户重传 -> 确认收款 -> 推动业务状态 -> 收据/付款确认记录 -> 退款/作废/审计。

### 15.3 付款订单状态

| 状态 | 说明 | 业务影响 |
| --- | --- | --- |
| 草稿 | 订单未正式展示 | 不影响申请 |
| 待付款 | 等待用户付款 | 申请可处于待缴费 |
| 已上传凭证 | 用户提交 Bank Transfer 凭证 | 等待财务审核 |
| 待财务审核 | 财务检查凭证 | 不进入最终通过 |
| 已确认收款 | 财务确认有效 | 推动申请进入审核/续期/复审 |
| 付款失败 | 网关或人工确认失败 | 用户需重新处理 |
| 重复付款待处理 | 疑似重复支付 | 财务人工处理 |
| 退款申请中 | 用户或后台发起退款 | 等待财务处理 |
| 已退款 | 退款完成 | 业务状态按规则回退或关闭 |
| 已作废 | 订单作废 | 不能继续付款 |

### 15.4 财务规则

- 财务审核和业务审核应分离。
- 凭证驳回必须写原因，用户可重传。
- 已确认订单原则上不回退，需通过退款、作废或修正事件处理。
- 退款必须记录原因、审批人、时间、金额、币种和关联业务。
- 付款只代表进入审核或续期/复审处理资格，不代表业务审核通过。

## 29. 安全、隐私、审计与数据保留

### 29.1 安全要求

- 全站 HTTPS。
- 密码加密存储。
- 后台建议 2FA。
- 管理后台按最小权限原则授权。
- 关键操作二次确认。
- 证书状态变更、数据导出、权限修改、敏感附件访问写入审计。
- 证书查验接口限流，防止撞库。
- 上传文件服务端校验类型、大小和权限。

### 29.2 隐私要求

- 注册、申请、上传材料前必须展示隐私说明。
- 公开展示个人信息必须获得授权。
- 支持更正、撤回公开、注销申请和数据导出申请。
- 后台导出敏感数据需记录用途和审批人。
- 数据泄露处理流程需上线前由法务和技术确认。

### 29.3 数据保留规则

| 数据类型 | 保留规则 | 说明 |
| --- | --- | --- |
| 付款凭证 | 按财务与法务要求保留 | 不公开，访问需财务/审计权限 |
| 证书 PDF/vt 记录 | 证书生命周期内及归档期 | 历史证书继续可验证 |
| 审核记录 | 长期保留 | 认证公信力和争议处理依据 |
| 公开授权 | 长期保留 | 包括撤回记录 |
| 投诉申诉 | 长期或按法务要求 | 争议处理证据 |
| 审计日志 | 长期或按技术/法务策略 | 高风险操作必须留痕 |

## 34. 验收标准

### 34.1 业务验收

- 访客可以从首页进入会员认证、证书查验、发展合作和数据中心。
- 用户可以完成注册、资料补全、申请提交、付款、补件、进度查询。
- 认证可以完成材料提交、初审、复审、付款确认、签发、核验、复审和争议处理。
- 证书可以按编号和姓名核验，并继续使用 vt 详情访问机制。
- 合作线索可以提交、分配、跟进、关闭和归档。
- 数据中心条目可以录入、审核、授权、公开、纠错、撤回和归档。

### 34.2 管理验收

- 后台角色权限隔离有效。
- 初审/复审、财务/业务审核职责分离。
- 高风险操作有二次确认和审计。
- 数据导出有审批和用途记录。
- 通知、待办、超时和失败重试可追踪。

### 34.3 合规验收

- 认证、证书、道医养生、易学 AI、数据公开、未成年人、退款等标准文案已确认。
- 个人库默认不公开。
- 公开字段逐项授权。
- 敏感材料不公开。
- 投诉、申诉、纠错有处理闭环。

### 34.4 本轮交付验收

- 本轮不执行 SQL。
- 本轮不修改数据库。
- 本轮不修改业务代码。
- 本轮不发布 production。
- 本轮不推翻 V1.3 编号、付款、证书 PDF/vt、核验、后台审核和历史数据。
